# TaskFlow Pro 企业可用性评估与完善方案

本文回答一个问题：**以「企业可直接使用」为标准，这个项目现在处在哪、还差什么、按什么顺序补。**

写作原则与 `docs/QUALITY.md` 一致：每条结论都指向可复现的证据（文件 / 行号 / 命令 /
数字），不写「已具备企业级能力」这类无法核查的话；**未实现与未验证的部分单列**，不与
已完成混排。

## 0. 边界与生效状态（必读）

原始规格 `团队任务协作系统_项目开发文档.md` 第 1 节的交付物定义是：

> 「形成一个可以用于 Python 后端求职、面试讲解和 GitHub 展示的完整项目」

也就是说，**这个项目的既定目标不是「企业交付物」，而是「高质量的可讲解作品集项目」**。
两者并不冲突，但要求不同：作品集要的是「架构清晰、技术点可解释」；企业交付要的是
「出事有人能定位、审计能过、数据丢了能恢复、换个人能接手运维」。

本文是**目标升级方案**，并且已经从「提案」变成「已落地的正式待办」（2026-09-16）：

| 项 | 落地位置 |
| --- | --- |
| 新增需求 | 写入规格 **§61 企业化需求**（`团队任务协作系统_项目开发文档.md`） |
| 决策记录 | `docs/DECISIONS.md` **062** |
| 任务定义 | `docs/TASKS.md` 的 **Phase 18~23 / TASK-088~127**（6 个 Phase、40 项）；`## Next` 指向 TASK-088 |
| 口径修订登记 | `docs/PROJECT_SPEC.md` **§7**（说明 §2/§5/§6 的哪些口径被修订） |

### 0.1 四个已确认的边界（用户拍板，决定了下面全部排序）

1. **目标形态：多租户 SaaS。** 这是全文**唯一的结构性改造**——全部业务表加 `tenant_id`、
   原先的全局唯一约束改为租户内唯一、RBAC 租户化、认证令牌携带租户、全部资源型端点的
   隔离测试重写。**它不是加法。**
2. **交付底座：Docker Compose 与 Kubernetes 都要。** 私有化走 Compose、云上走 K8s，
   健康检查必须同时满足两种探针语义。
3. **身份档位：本地账号加固 + MFA（TOTP）+ 企业目录（OIDC/LDAP）。**
4. **不做「最小可交付版」。** 按 Phase 18~23 全部推进，按批次实施与验收（见 §5）。

### 0.2 四个未决点按默认值推进（可推翻）

邮件通道 = 抽象 + 可插后端、默认企业自有 SMTP；附件存储 = 对象存储（S3/MinIO）作为
本地后端的对等实现；合规档位 = 个保法 + GDPR 口径（**不承诺**等级保护认证）；
分页口径 = 显式 `COUNT(*)` + `total`。四项都**不阻塞**当前批次，推翻时须同步改本节、
规格 §61 与对应 TASK。

### 0.3 一处需要更正的初稿结论

本文初稿写「后续工作**基本是加法**」——这句话在**多租户**这一项上不成立（见 §0.1 第 1 点），
其余 35 项成立。原因见 §4.1。

的功能（邮件、通知跳转、精确分页）。这些东西的共性：**它们不体现在代码优雅度上，
却是采购评审、安全评审、上线值班表上的必答题。**

## 2. 缺口清单

分四类。每项格式：**现状（证据）→ 企业影响 → 处置**。

### A 类：规格自己承诺了、但没做完（「欠债」，优先级最高）

欠债的性质比「缺新功能」严重：**文档说了有、实际没有**，接上去的人会先撞一次墙。

#### A1 §32 健康检查 3 个端点只实现了 1 个

- **规格 §32 原文**要求提供 `GET /health`、`GET /health/db`、`GET /health/redis`。
- **实测**：`app/main.py` 只定义了 `GET /`（第 71 行）与 `GET /health`（第 103 行）；
  全仓库 grep `health/db|health/redis` → **0 命中**。另两个端点是 **404**。
- **更糟的是文档仍在承诺**：`docs/DEPLOYMENT.md` 第 96–100 行「健康检查 → 应用：
  `/health`、`/health/db`、`/health/redis`」。监控团队照着接三个探针，两个直接 404。
- **影响**：企业侧的存活探针、DB/Redis 独立告警都无法按规格落地。
- **处置**：要么补齐三端点，要么订正 DEPLOYMENT.md 并说明为何改为单端点。**推荐补齐**，
  因为下面 A2 刚好需要它们。

#### A2 存活与就绪没有分离（编排层的硬需求）

- **现状**：`app/main.py` 的 docstring 自己写明「`/health` 总是返回 200，只要进程活着」
  （第 5–6 行、第 103–115 行）。这是个**站得住的设计**（避免依赖抖动导致容器被反复重启），
  但它只覆盖了 liveness 的语义。
- **缺的是 readiness**：数据库断连时 `/health` 依旧 200 → K8s / 编排系统认为实例「就绪」，
  继续把流量打进来 → 全量 5xx。这是编排环境里最常见的自伤。
- **处置**：`/health/live`（进程，恒 200）+ `/health/ready`（依赖，不可用时 503）+
  `/health/db`、`/health/redis`（单依赖明细）。compose 的 healthcheck 改用 ready。

#### A3 §1 交付物里的「指标」是 0 实现

- **规格 §1** 的交付清单写着「基础健康检查、日志与**指标**」。
- **实测**：全仓库 grep `prometheus|metrics|opentelemetry|sentry` → **0 命中**。
- **现状能做到的**：结构化 JSON 日志 + `X-Request-ID` 三层串联（这部分做得很好）。
- **影响**：**没有任何量化能力**——QPS、P95 延迟、5xx 率、DB 连接池占用、Celery 队列
  积压、限流触发次数全都看不见。没有指标就没有告警，没有告警就只能等用户报障，
  也就无法承诺任何 SLO。企业运维的第一道门槛就在这里。
- **处置**：`/metrics`（Prometheus 文本格式）+ 关键指标 + 示例告警规则；日志聚合
  （Loki/ELK）作为配套。

#### A4 §21/§44 的「JWT 黑名单」只定义了 Key，没接入校验链路

- **实测**：`app/core/redis_keys.py:91` 定义了 `jwt_blacklist_key()`，且其 docstring
  **自认**：「本 TASK 只定义 Key 约定；**接入校验链路是后续任务**」。认证依赖链
  （`app/core/deps.py`）里没有任何黑名单判定。
- **影响**（这条在企业安全评审里几乎必被问到）：
  1. 用户点「登出」后，**Access Token 在 TTL 内仍然有效**（默认 30 分钟）；
  2. 管理员**禁用账号**后，该用户手里的 Access Token 同样能继续用满 30 分钟；
  3. 改密码后旧 Access Token 不失效；
  4. **没有任何「强制下线」入口**——出了账号泄露事故，运维无事可做。
- **处置**：接上黑名单校验（登出 / 禁用 / 改密 / 会话下线时写入 jti），并把
  「会话列表 + 逐会话下线 + 全部下线」做成一个 TASK。

#### A5 §45 提到的 `EXPLAIN ANALYZE` 未做

- 已在 `docs/QUALITY.md` 第 5 节显式记录（「未做——项目规模下索引已足够，且没有慢查询
  报告驱动」）。**这个理由在作品集语境下成立，在企业语境下不成立**：企业要的是
  「有慢查询门槛 + 有基线」，而不是「暂时不需要」。归入 C6。

### B 类：企业安全/合规评审必然问到、当前完全没有

#### B1 密码策略零约束，且没有找回路径

- **实测**：`app/schemas/user.py:24` 是裸的 `password: str`——**没有 `min_length`、
  没有复杂度校验、没有弱口令黑名单**。也就是说 `123456` / `a` / 与用户名相同都能注册。
- 全仓库 grep `reset_password|password_reset|forgot` → **0 命中**：**没有密码重置流程**。
- 也没有：强制改密、密码过期、密码历史（禁止复用旧密码）。
- **企业影响**：这是安全评审的第一张表。没有找回路径还意味着**运营成本的现实问题**——
  用户忘记密码只能让 DBA 改数据库。
- **处置**：`UserCreate` 强校验（长度 + 字符类 + 常见弱口令 + 不得包含用户名/邮箱）+
  改密端点 + 重置流程（依赖 D1 的邮件能力）。

#### B2 没有账号锁定、没有登录专项限流、没有验证码

- **实测**：暴力破解只靠全站统一限流兜底——`app/core/middleware.py:157-163`，所有
  `/api/v1` 请求共用 `RATE_LIMIT_REQUESTS=60 / 60s` 一个配额，**登录端点没有更严格的
  独立配额**。
- 没有：失败次数计数、指数退避、锁定/解锁、验证码、异常登录告警。
- **影响**：60 次/分钟 × 分布式 IP 足以在线喷洒弱口令（何况 B1 允许弱口令存在）。
  「密码错误」与「账号不存在」文案统一这一点做对了（防枚举），但挡不住喷洒。
- **处置**：失败计数 + 渐进延迟 + 锁定阈值与自动解锁 + 登录独立限流 + 安全事件日志。

#### B3 没有 MFA，也没有 SSO

- 全仓库 `mfa|totp|otp|2fa` / `sso|oidc|saml|oauth` → 0 命中。
- **影响**：中大型企业私有化部署通常把「接企业目录（OIDC/LDAP/AD）或至少 TOTP」列为
  **上线前置条件**。没有它，这个系统在采购流程里会在「账号体系」一节被卡住。
- **处置**：TOTP 与 OIDC 分两个 TASK，**可开关**（不默认开启，避免把小规模部署搞复杂）。

#### B4 JWT 没有 `iss` / `aud` / `kid`，密钥不可轮换

- **实测**：`app/core/security.py:64-69` 只签 `sub` / `type` / `iat` / `exp`；单 HS256
  对称密钥（`Settings.jwt_secret_key`）。
- **影响**：① 无法轮换密钥（轮换 = 全员掉线，因为验证端只认一个密钥）；
  ② 无法区分签发方；③ 出了泄露事故，密钥变更没有平滑过渡方案。
- **处置**：加 `iss`/`aud` 声明 + 多密钥（`kid`）验证窗口（新密钥签发、旧密钥在
  TTL 内仍可验签），给出轮换 runbook。

#### B5 Refresh Token 没有重用检测，也没有会话管理

- **实测**：`app/services/auth.py` 的 `rotate_tokens` 对「已撤销的 jti」一律 401，
  但**不会吊销同一用户的其他会话**——即经典 refresh token reuse detection 缺失。
  也没有「登录设备 / 会话列表」端点。
- **影响**：Token 被复制使用时，攻击者与合法用户会互相踢对方下线（表现为随机掉线），
  但**没有任何一方收到告警**，事故不可见；用户也无法「我看看我登录了哪些设备，把
  可疑的那个下线」。
- **处置**：发现已撤销 jti 复用时，吊销该用户**全部** refresh token 并记录安全事件；
  暴露会话列表与下线端点。

#### B6 传输层与浏览器侧安全头不完整

- **现状（做对的部分）**：`nosniff` / `X-Frame-Options` / `Referrer-Policy` 两层 nginx
  都配了且带 `always`；`server_tokens off`；附件不直出（避免绕过鉴权的 IDOR）。
- **缺**：① `Content-Security-Policy`（**0 命中**）——这是 XSS 纵深防御的最后一道，
  评审必查；② `Permissions-Policy` / `COOP` / `COEP`；③ **TLS 未落地**：nginx 只
  `listen 80`、不发 HSTS——`docs/DEPLOYMENT.md:85-90` 明确写「TLS 由上游负载均衡终止」。
  这个取舍本身是对的（证书不进仓库），**但企业交付需要一个「谁在哪一层终止 TLS、
  证书怎么续期」的明确落地件**，而不是一句交给上游。
- **处置**：CSP 落地（navigate-to 报告模式先观察）+ 安全头补全 + TLS 二选一落地
  （本层 443 + 证书挂载 + HSTS，或交付上游 LB 的等价配置要求与验收清单）。

#### B7 附件的「恶意内容」防线

- **实测**：`app/services/storage.py` 的上传防护很扎实——不信任 `Content-Length`
  边读边计数、随机文件名与用户输入解耦、双层路径穿越校验（语义 + 真实路径 assert）、
  超限清理半成品。这部分是**教科书级**的。
- **缺**：① **无病毒/恶意内容扫描**（`clamav|antivirus` 0 命中），类型判定依赖扩展名
  白名单 + 客户端声明 MIME；② 存储只有 `LocalStorageBackend`——虽然
  `StorageBackend` Protocol 已为对象存储预留（§17 的设计意图），但**没有第二实现**，
  且文件落在 compose 命名卷上 → **单机绑定**，无法多副本、无法横向扩容、无配额；
  ③ 无按资源的下载/导出配额（仅受全站统一限流）。
- **处置**：magic bytes 内容嗅探 + 可选 ClamAV 钩子 + S3/MinIO 后端实现 + 配额。

#### B8 危险默认值（便利性换来的部署事故源）

- `app/core/config.py:24`：`debug: bool = True`（生产靠 compose 显式覆盖为 false）
- `app/core/config.py:61`：`jwt_secret_key: str = "change-me"`
- `app/core/config.py:27`：默认连接串里是 `postgres:postgres`
- **影响**：这三个默认值让「不配任何环境变量也能跑起来」——**这正是企业部署事故的
  常见来源**：staging 直接沿用默认密钥、某个容器漏传 `DEBUG`、明文口令进日志。
  生产 compose 已经有 `${VAR:?}` fail-fast（做得好），但**那是 compose 的功劳，
  不是应用自己的防线**。
- **处置**：应用在 `APP_ENV=production` 时**自检并拒绝启动**（默认密钥 / 默认口令 /
  `DEBUG=true` / 空 `TRUSTED_PROXY_IPS` 而开了 `TRUST_PROXY_HEADERS`）。

#### B9 5xx 没有统一信封，也没进结构化日志

- **实测**：`app/main.py:68` 只注册了 `AppError` 一个 handler。未捕获异常走 Starlette
  默认的 `text/plain` 500。
- **影响**：① 客户端无法统一处理（一会儿 `{"detail":...}`、一会儿纯文本）；
  ② 500 不进 JSON 日志的 error 字段 → SRE 无法按 `request_id` 聚合错误、无法做
  错误率告警。第 26 节「统一响应」的承诺在 500 这条路径上是破的。
- **处置**：全局 `Exception` handler → 统一信封（对外不含堆栈）+ 结构化 `exc_info` 日志
  + `request_id` 关联。

#### B10 限流没有分级

- **实测**：单一 `60/60s` 覆盖全部 `/api/v1`（`app/core/middleware.py:160-161`）。
- **缺**：按端点/按成本的差异化配额（上传、搜索、导出、批量操作的成本差几个数量级）。
- **处置**：配额表可配（默认沿用现值），登录/上传/导出单独设档。

### C 类：工程与运维（「可运维」是「可用」的前提）

#### C1 两个维护任务**永远不会执行**（最高优先级的技术缺陷）

这是本轮审计里最「值钱」的一条发现。

- **实测**：`app/tasks/maintenance_tasks.py` 实现了 `archive_operation_logs`（日志归档）
  与 `cleanup_expired_attachments`（孤儿附件清理），两者都有重试/幂等/超时，且有 13 项
  测试（`tests/test_maintenance_tasks.py`）+ 2 项经 Celery 任务机的端到端用例
  （`tests/test_task_resilience.py`）。
- **但是**：
  - 全仓库 grep `beat|crontab|beat_schedule|periodic` → **0 命中**；
  - `docker-compose.yml` 与 `docker-compose.prod.yml` 都**只有 `celery_worker`，没有
    `celery_beat`**；
  - 两个任务的**唯一调用点在测试里**（`archive_operation_logs.delay(...)` 只出现在
    `tests/`）。
- **结论**：**生产环境里，操作日志只增不减、孤儿附件只增不减。** 定时归档与清理是
  100% 未生效的死代码——它「实现了」，但「没有运行」。
- **影响**：① `operation_logs` 无限增长（企业跑一年后这张表会是最重的一张）；
  ② 上传中断/删除任务留下的孤儿文件永久占用存储；③ A 类欠债 + 本项叠加后，
  **日志归档到 `operation_logs_archive` 之后也没有终态删除策略**——即「数据永久保留」，
  这在个保法/GDPR 语境下反而是合规风险（存储期限最小化）。
- **处置**：`celery_beat` 服务 + `beat_schedule`（错峰、可配）+ 「任务真的会被调度」的
  契约测试 + 归档表的终态保留策略。**这是本方案里投入产出比最高的一项。**

#### C2 没有备份与恢复

- 无 `pg_dump` 定时任务、无卷快照、无恢复脚本、无 RPO/RTO 声明（grep `pg_dump|backup`
  在非测试代码里 0 命中）。
- **影响**：数据丢失是**不可逆**的。企业上线前一定会问「备份策略是什么、多久、怎么恢复、
  演练过吗」。当前答案是「没有」。
- **处置**：数据库定时备份 + 附件卷备份 + **恢复演练脚本**（并在文档里写清 RPO/RTO）。

#### C3 没有资源上限与扩缩容路径

- compose 无 `cpus` / `mem_limit`；Gunicorn worker 数靠 `WEB_CONCURRENCY` 手工；
  Celery 无队列分级与并发上限说明；**无 K8s / Helm 清单**。
- **并且有结构约束必须先说明**：附件落在**本地命名卷**上 → 多副本部署时文件不共享
  （A7/B7 的对象存储在这里再次成为前置项）；Celery 单 worker 队列 → 无优先级隔离。
- **处置**：资源 limits + 容量估算文档 +（可选）K8s/Helm，并明确「多副本前必须先上
  对象存储」。

#### C4 没有供应链安全

- 无镜像扫描（trivy/grype）、无 SBOM、无 `dependabot` / `renovate`、无
  `pip-audit` / `npm audit` 门禁（全部 0 命中）。
- **处置**：三件套——依赖更新 PR 自动化 + CI 加依赖漏洞扫描 + 镜像扫描与 SBOM 产出。

#### C5 没有发布流程与环境分离

- CI 只验证不部署（这个取舍**是对的**，理由写在 `.github/workflows/ci.yml` 里）。
- **缺**：staging 环境、迁移上线门禁（CI 已验可逆性，但缺生产实操流程）、
  灰度与回滚判定、变更记录。企业上线要求「能上、能回、能说清上了什么」。

#### C6 没有性能与容量基线

- 无压测（k6/locust）、无慢查询门槛、无连接池参数与容量估算。
- A5（`EXPLAIN ANALYZE`）与这项合并。

#### C7 观测链路断在最后一步

- 现状：**应用出口的输出质量很高**（§33 JSON 十字段、脱敏、request_id 三层串联、访问日志）。
- **缺**：日志**聚合**（Loki/ELK）、指标（A3）、追踪、告警规则、on-call runbook。
- **影响**：出故障只能 `docker logs` 人肉翻——日志写得再好，没有检索与告警就等于没有。

#### C8 一处文档漂移，且护栏没覆盖这类不变量

- `docs/DEPLOYMENT.md:96-100` 声称 `/health/db`、`/health/redis` 存在（实为未实现，见 A1）。
- `scripts/check_docs.py` 的不变量集很严（进度↔任务、README↔规格、数量↔文件系统），
  但**不含「文档中声明的端点必须存在于 OpenAPI」**这类语义一致性。
- **处置**：订正漂移 + 把这条不变量加进护栏（顺手让 A1 不可能再次漂移）。

### D 类：产品功能（决定用户「用得下去吗」）

#### D1 没有任何邮件能力

- 全仓库 `smtp|sendmail|send_email|EmailMessage|EmailStr` → **0 命中**。
- **具体后果**：
  1. **邀请成员**只能由邀请人先知道对方是谁再搜（TASK-085/086 已经把「手填数字 ID」
     改善成「按名字/邮箱搜」，但**被邀请人完全不知情**，得靠微信/口头通知）；
  2. **密码找回不存在**（见 B1）；
  3. 无通知邮件摘要 → 用户不登录就收不到任何提醒（站内通知的到达率等于「用户主动打开」）。
- **影响**：企业协作工具的**通知到达率**主要靠邮件/IM。缺这一条，用户会觉得「这系统
  不如微信群」。这也是 D1 排在 D 类第一位的原因。
- **处置**：SMTP 抽象（可插企业自有 SMTP / 云 SES）+ 模板 + 走 Celery 队列 + 退信处理。

#### D2 通知点不进去

- `NotificationRead` **没有 `link` / `resource_id` 字段**，资源 id 只以文本嵌在 `content`
  里；前端按 DECISIONS 054 **诚实地不跳转**（不解析正文猜 id）。页面顶部有 `el-alert`
  明示。
- **影响**：用户看到「任务已分配给你」，点不动。这是**高频断点**，也是「降级」里最影响
  体感的一个。
- **处置**：后端补 `link` / `resource_type` / `resource_id` 字段（**输出侧新增，不破坏
  既有契约**），前端接线跳转，关闭 D15。

#### D3 通知触发点太少

- **实测**：唯一的业务触发点是 `app/services/task.py:84`——任务分配 + 状态流转。
- **缺**：评论通知、**@提及**、任务到期提醒、项目/团队变更通知、被移除出团队通知。
- **处置**：先补「评论 + @提及」（协作工具的核心回路），再做到期提醒（依赖 C1 的 beat）。

#### D4 列表没有 `total`，分页是「上一页/下一页」

- **实测**：8 个列表端点统一 `skip` / `limit` + 纯列表响应，**不返回 `total`**
  （TASK-035 起的确认决策，`docs/QUALITY.md` 第 8 节 D1 已完整披露，含代价与残余风险）。
- **影响**：① 无法显示「共 N 条 / 共 M 页」；② 偏移量分页在并发写入下可能**跨页重复或
  漏项**；③ 报表页、精确分页、数据导出都缺基础能力。
- **处置**：见 4.3 的方案分叉——**不要默默加一个 `COUNT(*)`**（大表上它是全表扫描），
  要么显式接受一次 count 查询，要么引入 cursor 分页。这需要重新决策，而不是顺手改。

#### D5 日志页信息不足

- 无筛选参数（类型/时间/操作人只能在前端已取回的页里筛）、无 IP、无操作人列
  （当前用户时间线）。企业审计场景下，「谁在什么时候从哪里做了什么」缺了「从哪里」。

#### D6 项目/团队统计缺失

- `ProjectRead` 无 `status` / 成员数 / 任务数 / 进度；team 无任务统计。
- 前端已诚实降级（顶部提示、不编造接口），但**管理视图是空的**——团队负责人看不到
  「这个项目还剩多少活」。

#### D7 没有跨项目的「我的任务」

- 受 D7/D8·Q2 阻塞（`GET /tasks` 的 `project_id` 必填、无全局任务端点）。
- **影响**：这是个人工作台的核心视图。前端只能靠「选项目 + assignee_id=我」表达，
  用户得**先想清楚任务在哪个项目里**——这违背了「我的任务」的语义。

#### D8 没有实时推送

- 通知靠前端刷新/轮询（`stores/notification.ts` 的预览请求 + 铃铛），无 WebSocket/SSE。

#### D9 没有批量操作与导入导出

- 无批量指派 / 批量流转 / 批量删除；无 CSV 导入成员；无数据导出。

#### D10 评论是纯文本

- `textarea` + 2000 字上限，无富文本、无 @提及、无附件内联、无编辑历史。

#### D11 没有数据主体权利工具（合规）

- 无「导出我的数据」、无「注销账号 / 删除我的数据」、无隐私声明与数据保留期声明。
- 与 C1 叠加：归档任务不跑 + 归档表无终态清理 = **数据永久保留**，这在个保法/GDPR 的
  「存储期限最小化」上是个反向问题。

#### D12 不可配置（可后置）

- 无自定义字段 / 自定义状态 / 工作流模板。企业项目常见需求，但**优先级最低**——
  先把上面这些补完再谈配置化。

## 3. 结论：现在能不能「企业直接用」

| 维度 | 判定 | 依据 |
| --- | --- | --- |
| 代码质量与分层纪律 | ✅ 够用 | 静态分层断言 + 运行时分层的测试钉死；99.96% 行 / 100% 分支（本地口径） |
| 测试真实性 | ✅ 够用 | 全量走真实链路（真 DB / 真 Redis / 真 Token），无 mock 掉被测行为的假绿 |
| 认证与授权基础 | ✅ 够用 | 双 Token + jti 落库 + 轮换 + 跨用户撤销拒绝；功能级 + 资源级双层校验；越权统一 404 防枚举 |
| 部署暴露面 | ✅ 优于平均 | 生产只有 nginx 对外，其余服务零宿主端口（结构保证 + 契约测试） |
| 审计日志 | ⚠️ 半成品 | 有三类 action 的落库与查询，但**归档任务不跑、无 IP、无终态清理** |
| **可观测** | ❌ **不达标** | 无指标、无告警、无日志聚合、无追踪（A3 / C7） |
| **可运维** | ❌ **不达标** | 无备份恢复（C2）、维护任务不调度（C1）、无发布流程（C5） |
| **身份体系** | ❌ **不达标** | 无密码策略（B1）、无锁定（B2）、无 MFA/SSO（B3）、会话不可下线（A4/B5） |
| **合规** | ❌ **不达标** | 无数据导出/注销、无保留策略（D11 + C1） |
| **用户可用性** | ❌ **不达标** | 无邮件（D1）、通知点不进去（D2）、无「我的任务」（D7） |

**一句话**：**不是一个「快好了」的项目，而是一个「地基很扎实、但缺了另外三层楼」的项目。**
地基（架构 / 测试 / 分层 / 安全边界）不用重做，这很关键——它意味着后面的工作**基本是
加法**，不会推倒重来。

> **例外（重要）**：用户确认目标形态为**多租户 SaaS** 后，Phase 19 是这条结论的例外——
> 它要给全部业务表加租户维度、把全局唯一约束改成租户内唯一、把 RBAC 与认证租户化。
> 这不是加法，是**结构性改造**，且会影响全部资源型端点的测试。其余 35 项仍是加法。

**当前状态下上生产的真实风险排序**（如果硬要上）：
1. 数据丢了救不回来（C2）——**不可逆，最高**
2. 出故障定位不了（A3/C7）——**不可控，次高**
3. 日志/孤儿文件无限增长（C1）——慢性的，但要几个月后才疼
4. 账号安全扛不住评审（B1/B2/A4）——**卡在采购环节，不是技术故障**
5. 用户用不下去（D1/D2/D7）——**决定留存**

## 4. 路线图（已登记为 Phase 18~23 / TASK-088~127）

任务的事实来源是 **`docs/TASKS.md`**——每项都含目标、依赖、涉及文件、实现要求、验收标准、
测试要求六要素。本节**不重复任务定义**，只回答一个问题：**为什么是这个顺序。**

| Phase | 主题 | TASK | 关闭的缺口 |
| --- | --- | --- | --- |
| 18 | 生产可靠性地基 | 088~092 | A1 A2 A3 B8 B9 C1 C7 C8 |
| 19 | 多租户地基 | 093~100 | **结构性改造**（规格 §61.3）——不在初稿缺口清单里，由「多租户 SaaS」这一决策带出 |
| 20 | 身份与安全硬化 | 101~106 | A4 B1 B2 B3 B4 B5 B6 |
| 21 | 合规与数据治理 | 107~108 | D5 D11 |
| 22 | 产品补齐 | 109~118 | D1 D2 D3 D4 D6 D7 D8 D9 D10 |
| 23 | 工程化与交付 | 119~127 | A5 B7 C2 C3 C4 C5 C6 |

### 4.1 排序的三条理由

1. **先做与租户无关、且能降低风险的事。** Phase 18 的五项（健康检查、调度、指标、
   配置自检、文档语义护栏）不碰数据模型，做完立刻是「能监控、能告警、知道维护任务在跑」。
   更关键的是：**Phase 19 要动全部业务表，改造期间最需要的恰恰是指标与健康检查**——
   先补齐它们，改造才有人看得见。
2. **身份与安全必须建立在租户之上。** 密码策略、登录防护、JWT 硬化、MFA、SSO 每一项都要
   回答「这是哪个租户的身份」。若先做 Phase 20 再做多租户，这六项全部要改第二遍。
3. **合规与产品往后放，但「不可逆」的两项不往后放。** 备份（C2，数据丢了救不回来）与
   调度（C1，日志与孤儿文件只增不减）属于「不做会不可逆」：C1 因此在前置的 Phase 18，
   C2 排在 Phase 23 首位。邮件、通知跳转、我的任务决定的是**留存**，可以边用边补。

### 4.2 每个 Phase 收尾的门禁

后端全量 pytest（基线 1037 只增不减）+ 前端四门（typecheck / lint / test / build）+
`python scripts/check_docs.py` 退出码 0。**未通过不得勾选**（项目规则 §13）。

## 7. 明确不做（避免为复杂而复杂）

延续项目规则 §15 与规格 §6 的取向，以下**不建议做**：

- **不引入第二个 Redis、不引入 Kafka / RabbitMQ**：当前规模下 Redis 同时承载限流、
  黑名单、Broker、Backend 是合理的（§21 明确如此）。要分也是按容量数据分，不是按「显得
  专业」分。
- **不引入 Elasticsearch**：`pg_trgm` + `tsvector` 已覆盖当前检索需求（TASK-064 有
  `EXPLAIN` 实证）。中文分词若真有需求，先评估 `zhparser` / `pg_jieba` 扩展。
- **不自研 SSO、不自建 CA**：接标准协议（OIDC）与用成熟组件。
- **不拆微服务**：当前分层（Router→Service→CRUD→Model）与单进程部署是匹配的；拆了
  只会把「一个事务能解决的事」变成分布式一致性问题。
- **不为覆盖率数字写空测试**：延续 Phase 14 的口径（`docs/QUALITY.md` 第 1.2 节已把
  「唯一未覆盖行」的做法固定下来）。
- **不把 `search_vector` 强制用于 `keyword`**：`'simple'` 配置不做中文分词，切过去会让
  子串检索**静默失效**（DECISIONS 045 已有双向断言固化）。这个判断是对的，继续保持。

## 8. 验收：企业可用的判定清单

上线前逐条打勾（每条都是可验证的，不是形容词）：

**可靠性**
- [ ] 存活/就绪分离，依赖故障时实例被摘除而不是继续收流量
- [ ] 数据库备份按策略执行，且**恢复演练通过**（不是写了脚本没跑过）
- [ ] 维护任务（归档/清理）在真实环境**自动**执行，归档表有终态保留策略
- [ ] 生产配置错配时**拒绝启动**，不静默沿用默认密钥

**可观测**
- [ ] `/metrics` 暴露请求率/延迟/错误率/连接池/队列深度
- [ ] 每条告警规则都有对应 runbook（现象 → 排查 → 处置）
- [ ] 500 走统一信封且带 `request_id` 进结构化日志
- [ ] 日志可聚合检索（不再 `docker logs` 人肉翻）

**安全**
- [ ] 密码强度校验生效，且能自助重置
- [ ] 暴力破解有锁定与专项限流
- [ ] 登出/禁用/改密后 Access Token **立即**失效；有「会话列表 + 强制下线」
- [ ] JWT 支持密钥轮换（`kid` + 验证窗口）
- [ ] CSP 已 enforce（或 Report-Only 的违规项已逐条解释）
- [ ] TLS 落地位置明确，证书续期有主

**合规**
- [ ] 用户可导出自己的数据、可注销账号
- [ ] 每类数据的保留期有明文声明且**由代码执行**（不是只写在文档里）
- [ ] 审计日志有 IP 与筛选，且应用账号无 UPDATE/DELETE 权限

**运维**
- [ ] staging 环境可用，发布有清单与回滚步骤
- [ ] 依赖漏洞扫描与镜像扫描进 CI
- [ ] 容量与连接池参数有依据（压测数据 + `EXPLAIN ANALYZE`）

**用户可用性**
- [ ] 邀请成员会**通知到被邀请人**
- [ ] 通知可点击跳转到对应资源
- [ ] 有跨项目的「我的任务」
- [ ] 列表分页口径统一且有 `total` 或明确的 cursor 语义
